# 审查方法与维护约定

## 目的

这组文档用于把项目探索结果沉淀成可复核的工程知识，而不是一次性的主观点评。审查结论必须能回到源码、配置、构建脚本或现有文档；无法确认的内容要明确标记为推断或待验证。

## 证据优先级

1. 当前分支源码、配置和可执行脚本。
2. 同一提交中的测试、构建日志和运行说明。
3. `docs/`、`DESIGN.md`、`AGENT.md` 等项目文档。
4. 依赖的官方文档与仓库示例（仅在源码无法说明意图时引用）。
5. 个人经验只能作为建议，不能作为项目事实。

每条重要结论至少记录一个文件路径和行号；涉及行为时同时记录触发入口、关键调用链和验证状态。

## 结论标签

- **已确认**：有直接源码/配置证据，且不依赖未验证的运行环境。
- **已验证**：除源码证据外，还通过针对性构建、测试或真实运行路径复核。
- **风险提示**：当前未必已经失败，但存在可解释的脆弱点。
- **待验证**：缺少环境、平台、数据或用户路径证据，不能提前宣称通过。

## 审查边界

- 先描述当前行为，再提出建议，避免把偏好写成缺陷。
- UI 结论必须参考 `DESIGN.md` 和对应的 `docs/examples/`/`docs/aielements/` 示例。
- 发布、安装、升级、数据清理等运行态结论，必须区分源码构建、打包、安装和安装后启动。
- 依赖或借鉴关系只有在源码导入、配置、注释、锁文件或官方来源可追溯时才写成事实。
- 不在这组审查文档中记录密钥、个人数据、机器专属绝对路径或不可公开的日志内容。

## 维护流程

1. 每次较大的架构、构建或 UI 变更后，更新受影响章节和证据行号。
2. 发现问题时先归类为缺陷、风险或待验证项，再按 `03-common-issues-severity.md` 的等级排序。
3. 修复问题后保留原问题的根因、修复提交和验证结果，不只删除问题描述。
4. 每个季度或一次重大版本发布前，复查文档中的“待验证项”和过期路径。
5. 新增原则必须能映射到至少一个真实消费者；没有消费者的抽象原则放入候选项，不强行推广。
